# 帰属イベントの内容裏付け表示 仕様書 v1.0

作成日: 2026-07-26
発端: 受入実測（2026-07-26・人間確認21件）で `incorrect` となった2件

---

## 1. 解く問題

帰属（linked / broken）の refs に、**その変更を作っていない編集**が混ざる。

実測で見つかった2件:

| ケース | ツールの主張 | 実際 |
|---|---|---|
| `src/eval/cases.ts:206` | この行を作ったのは A と B | A は作っている。**B は作っていない**（B の差分にこの行は無い） |
| `src/eval/cases.ts:145` | この変更を作ったのは B | B が一致しているのは**空行1行のみ** |

原因は、帰属を**行の位置の重なり**だけで決めているため。
位置が重なる ≠ その行を書いた。同じ数行の範囲内で別の行を触っただけの編集も refs に入る。

`ask` は refs を「〜で AI が編集」と表示するため、**著者として読める**。
レビュアーは挙がった編集の会話を見に行くので、無関係な編集が混ざると誤った所に辿り着く。

## 2. 方針

**判定ロジックは変えない。** 位置追跡は捨てない（内容が同じでも別人が書いた場合を見抜けるのは位置追跡だけ）。
すでに計算済みの**内容一致**を使って、refs に印を付けるだけにする。

REQ-501: 帰属イベントごとに、その編集自身の差分が hunk の変更行を含むかを判定し、
`support` として記録する。

| support | 意味 |
|---|---|
| `author` | この編集の差分に、hunk の変更行（情報量のあるもの）が含まれる |
| `touched` | 同じ範囲を触っているが、hunk の変更行は含まれない |
| `unknown` | スナップショット欠落等で判定できない |

REQ-502: 判定は既存の突き合わせ規則をそのまま使う（符号付き・多重度保存・情報量のある行のみ／REQ-403/404）。
**新しい推定は増やさない。** 観測できる事実の提示だけを行う。

REQ-503: `support` はイベント（`lineage_linked`）に記録し、projection にも保持する。
confidence だけから証拠の種類を推測させない。

REQ-504: `ask` は refs を support で分けて表示する。

```
この変更を作った編集:
  - 2026-07-26T11:29 の op_xxx (claude-code)
同じ範囲を触っただけの編集(この変更は作っていない):
  - 2026-07-26T11:31 の op_yyy (claude-code)
```

REQ-505: `author` が1件も無い場合、その旨を明示する
（「範囲は重なるが、この変更を作った編集は特定できていません」）。

REQ-506: 判定（linked / broken / candidate / uncaptured）と confidence は**変更しない**。
表示と記録の追加のみ。既存テストは期待値を緩めずに通ること。

REQ-507: 受入計測のケースにも support を含め、判定者が「作った/触っただけ」を区別できるようにする。

## 3. 受入条件

1. 既存テストが全て通る
2. 実測で `incorrect` となった2件と同じ形（内容一致のない ref が混ざる）で、
   `touched` として区別されることをテストで固定する
3. `ask` が `author` と `touched` を混ぜて表示しない
4. `author` が無いケースで、著者を断定しない
