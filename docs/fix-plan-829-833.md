## REQ-829 non-ASCII ファイル名が黙って消える

### 症状（実測済み）

`git ls-files` は既定でnon-ASCIIをoctal-quoteする。

```
$ git ls-files
ascii.md
"\346\227\245\346\234\254\350\252\236.md"
```

`buildWorktreeRevision` はこの引用符付き文字列を `rel` として使い、
`fs.existsSync` が false になって `revision.ts:52` の `continue` で捨てる。警告なし。
実測: fixtureリポジトリで `設計メモ.md` は manifest に現れない。

### 修正

1. `git ls-files` / `git ls-tree` に `-c core.quotepath=off` を付ける（`src/ingest/revision.ts`）
2. **worktree側**: `fs.existsSync` が false だった `rel` を集め、
   ingest の warnings に**ファイル名つき**で出す。現状は無音で `continue`
3. **commit側**（v1で欠落・fable指摘）: `buildCommitRevision` の per-file `cat-file` 失敗を
   ファイル単位で捕捉し、同様に warnings + skipped へ。現状 `--range` では raw git fatal が出る
4. **例外の握りつぶしを潰す**（v1で欠落・fable指摘）:
   `commitHeadRefOrEmpty`（ingest.ts:319-325）の `catch { return null }` が、
   クラッシュを「対象なし(baseとheadに差分がありません)」という誤ったメッセージに変えている。
   fallback したときは warnings に理由を出す
   → **次に revision 周りで壊れたときも同じ無音化が起きる**ので、ここは必ず塞ぐ

`-z` ではなく `core.quotepath=off` を選ぶ理由: 出力パーサ（`split("\n")` と ls-tree の正規表現）の
書き換えが不要。**ただし改行入りファイル名は依然として扱えない**。これはコード注釈に残す。

### 移行時の影響（v1で欠落・fable指摘）

修正後の初回ingestは、non-ASCIIファイルを**含まない**旧head manifestとの差分になるため、
それらが**ファイル全体の追加hunkとして大量に出る**。回帰ではない。
`input_digest` も変わるので dedupe されない。**リリースノートに1行書く。**

### テスト

1. **fixtureベース**で `buildWorktreeRevision` の manifest に日本語名ファイルが入る
   （red-green の red は**正規表現の単体テストではなくこのfixtureテスト**にすること・fable指摘）
2. 同fixtureで capture→ingest まで通し、そのファイルのhunkが生成される
3. 読めないパスがあるとき warnings に**ファイル名**が出る
4. commit revision 構築に失敗したとき warnings に理由が出る

## REQ-830 「観測していない前後関係」を支持と断定しない

### 830-A 事前存在の判定 — **両レビュアーの見解が割れた。判断を仰ぐ**

v1案: 仕様書ファイルの最古の捕捉編集が `pre_blob_hash IS NOT NULL` なら、
そのファイルは観測開始前から存在 → `事後` と断定しない。

**fable**: この不変条件は正しい、とコードで確認。
`capture.ts:135-137` + `putObject` は binary/oversize でも hash を返すため、
記録済みイベントの範囲で `pre_blob_hash IS NULL ⟺ pre-hook時点でファイルが通常ファイルとして存在しなかった`。
空ファイル→非NULL、読めないファイル→イベント自体が記録されない、も確認済み。

**codex**: 不変条件は認めるが**的が外れている**。
ファイルが前から在っても、**支持根拠の段落を今日追記した**なら事後であるべき。
代案は「**編集前の内容（pre blob）に、その要求が実際に入っていたかを比較する**」。

**私の判断: codex案を採る。** 理由は、これがファイル単位という近似そのものを消すから。
`getObject(ws, hash)` で編集前の中身を復元できることは確認済み（実装可能）。
fableが確認した不変条件は、その**取り出し口**として使う。

fable も2巡目で「codex が正しい。統合は妥当」と明言（自案は「*ファイル*が観測前から在ったか」に
答えるもので、REQ-824 の問いは「*要求*がコードより前から在ったか」だった、と）。

### 手順（v3。fable の指摘で3箇所を修正）

**T の定義**: `authorOps` の `MIN(ts_pre)`（現行コード heuristics.ts:67-72 と同じ基準）。
hunk に author が複数あるとき MIN/MAX で結果が変わるので明示する。

1. コード変更の author 編集の時刻 **T = MIN(ts_pre) over authorOps** を得る
2. 仕様書の捕捉編集のうち **T 以前の最新** V を探し、`result(V)` の内容を見る
   - REQ が**在る** → `支持`（後述の非対称性により追加検査は不要）
   - REQ が**無い** → **そのままでは `事後` にしない。連続性を検査する**（下記 c-1）
3. V が無い（＝捕捉編集はすべて T より後）→ 最古の捕捉編集 U の `pre_blob_hash` の内容を見る
   - **`pre_blob_hash` が NULL なのは「答え」であって「取得不能」ではない**（fable指摘）。
     U > T の時点でファイルが存在しなかった＝ファイルごと T より後に作られた → **`事後`**
   - 内容が取れて REQ が無い → `事後` / 在る → `支持`
4. 上記で内容が取れない → `null`（断定しない）。
   **取れない原因を明記する**: purge 済みだけでなく、**binary/oversize は本文が保存されない**
   （`putObject` は hash を返すが `stored: false`・objects.ts:26）。
   5MB超の仕様書は毎回ここに落ちる。**hash だけから断定してはいけない**
5. 判定に使う語は REQ-ID だけでなく、**非明示経路では `bodyHits` の語も過去内容に在るか**を見る（下記 c-3）

### この手順が安全である理由（非対称性・fable）

- **ある時点 ≥ T で不在が観測された** → T より後に追加された、と言い切れる（`事後` は堅い）
- **ある時点 U > T で存在が観測された** → T 時点で存在したことは**証明しない**
  （捕捉外の編集が (T,U] で追加した可能性）→ ここは緩い側（`支持`）に倒す。REQ-824 の null 規則と同じ

### c-1 手順2の `事後` は未観測の隙間を跨いで断定してしまう（fable指摘・要修正）

V < T での不在は、**T 時点での不在を証明しない**。(V, T] に捕捉外の編集（ヒアドキュメント・手編集）が
あって REQ を足していれば、実際にはコードより前から在ったことになる。
これは中心原則が禁じる過剰断定そのもの。**codex が私の案に見つけた穴の鏡像。**

`事後` と断定する前に**連続性検査**を入れる（blob hash の比較のみ。内容 diff は不要）:

- W = V の次の捕捉編集（必ず W > T）。`pre(W) == result(V)` なら (V, W) ⊇ (V, T] は無変更
  → T 時点の不在が証明される → **`事後` 妥当**
  - 厳密には、これが証明するのは**両端の一致**であって区間内が不変だったことではない（fable指摘）。
    捕捉外で REQ を足し、W より前に戻せば擦り抜ける。
    ただし**意図的な「捕捉外での追加→復元」はこのツールのあらゆる機構を無効化する**ので、
    ヒアドキュメント回避と並べて**文書化された限界**として扱う（設計変更はしない）
- W が無い場合: `result(V)` と**取り込み対象 head revision のその仕様書の内容**を比較。一致なら無変更 → 妥当
- どちらも不一致 → 決定的な窓に捕捉外の変更がある → **`null`。断定しない**

（存在側には不要。存在は「T以前のいずれかの観測時点で在った」で足りるため）

### c-2 同一操作・時刻タイの扱い（fable指摘・要明記）

codex の `apply_patch` は `filesPerOperation: "many"` で、
1操作が `docs/spec.md` と `src/x.ts` を同時に編集しうる。
各ファイルの `edit_pre` はファイル反復順に連続 append されるだけで、
**ミリ秒未満の順序は事実上任意**。ここで「T より前」を判定するのはコイン投げになる。

規則: **仕様書の編集がコードの author 編集と `operation_id` を共有する、または `ts_pre` が等しい場合は
`支持` 側に倒す。** 仕様とコードを*同時に*書くのは REQ-824 が問題にしている後付けの正当化ではない。
曖昧なら緩い側、という全体規則とも一致する。**1操作内の行間でサブミリ秒順序に依存しない。**

### c-3 REQ 書き換えの抜け穴（fable指摘・部分対処＋文書化）

手順5が「REQ-ID の文字列が過去内容に在るか」だけを見ると、
**T 時点に `REQ-903` は在ったが中身が別物で、今日それを書き換えて自分の変更に合わせた**場合、
IDは在るので `支持` になる。実務では「新しいREQを足す」より
**「既存のREQを自分がやったことに合わせて書き換える」方が自然な自己正当化**であり、こちらの方が起きやすい。

部分対処: **非明示経路では、一致した `bodyHits` の語も過去内容に在ることを要求する。**
明示参照経路（`bodyHits = [req_id]`）では語の検査を足しても意味がないので、
**ヒアドキュメント経由の回避と並べて「文書化された限界」として残す。**

### テスト（fable指摘で4件追加）

1. 仕様書は前から在るが該当REQ段落は後から追記 → `事後`
2. 仕様書も要求も前から在る → `事後` にならない
3. **捕捉外の編集が (V,T] に挟まっている → `事後` にせず `null`**（c-1 の red テスト）
4. **仕様とコードが同一操作 → `事後` にならない**（c-2）
5. **T より前の捕捉編集が無く、最古の捕捉編集の pre に REQ が無い → `事後`**（手順3）
6. **仕様書が T より後に capture 下で新規作成（pre が NULL）→ `事後`**（手順3のNULL扱い）
7. `posthoc=null` のとき confidence が最大値でない
8. null の3原因で reason が区別できる
9. candidate 帰属では `事後` にならない

**明示する決定（fable指摘・どちらか選べと言われた点）**:
上記の検索は **`status='completed'` のみ**を対象とする。
作成時の編集が `aborted`（postが失われた）の場合、2番目の編集（pre非NULL）が最古に見え、
**緩い側（事後にしない）に倒れる**。稀なケースで正当な `事後` を1件落とすが、
断定を増やさない方向なので許容する。**次の人が「バグ」として直さないよう、この一文を残す。**

**文書化する限界（fable指摘）**:
Bashのヒアドキュメント等（hook外）で仕様書を作り、その後 capture 下で編集すると、
最古の捕捉編集の pre は非NULL になり緩い側に倒れる。
これは「hook外の変更は捕捉不可」という既知の限界がここに現れたもの。
`docs/spec-setup-gaps.md` に1文で残す。

### 830-B 未観測時の値

現状: `posthoc === null` のとき `spec_support=支持` を **confidence最大**で設定。

**修正**: 値は `支持` のまま、confidence を `HEURISTIC_CONF_MAX`(0.5) より下げる（0.4）。

**v1に書いた「大半は明示REQ参照があるから」という理由は削除する**（fable指摘・未検証だったため）。
代わりに正しい根拠:
- `docs/spec-setup-gaps.md:87` が既に「捕捉されていなければ支持のまま、reasonに未観測と明記」と規定している。
  つまり `支持` 維持は**新しい判断ではなく既存仕様**で、本修正は confidence 低下を足すだけ
- `支持` が主張しているのは**内容の対応**であり、それは実際に観測されている。
  前後関係は潜在的な反証だが、**観測されていない反証は反証の証拠にならない**
- 値まで `判定不能` にすると「対応が観測されなかった」と「対応はあるが前後不明」が
  区別できなくなり、レビュアーにとって情報が減る

**null の原因は3種類あるので、reason を区別する**（fable指摘。再測定時に効く）:
(i) author が特定できない (ii) 仕様書の編集が未捕捉 (iii) 仕様書が観測開始前から存在

## REQ-831 指示判定を「対象語の一致数」だけで決めない

### 831-A ファイル名の脚に汎用語検査を入れる

`hitFiles` を `isDistinctiveTarget` で絞る。
`GENERIC_TOKENS` に汎用ファイル名幹を追加（`main` `utils` `helper` `common` `spec`）。
**`index` `test` `config` `types` は既に入っているので重複させない**（fable指摘）。

副作用として、`db.ts` のような短い名前は両脚とも6文字未満になりファイル脚を失い、
symbol 2件が必要になる。**断定を減らす方向なので許容。**
`test.ts` のような拡張子つきbasenameは7文字で残り、
`containsToken` は発話中にリテラルなファイル名を要求するので**強い信号として維持される**（fable確認）。

### 831-B 会話探索を author 優先・全イベントに広げる

現状 `linkedEvents[0]` 固定。refs は span 挿入順（最古のop先頭）なので、
**先頭が `touched` で真の author が後ろにいる**ことがある。
→ 実測の「recall漏れ」の真因はこれと見ている。

修正: `refSupport==="author"` のイベントを優先し、author が無い/複数なら
**全 linkedEvents の窓を順に探索**。1つでも成立すればその発話を根拠に採る。
探索上限 `UTTERANCE_SCAN_MAX` は各窓に適用。

### 831-C 否定表現

**設計は「断定条件に足す」のではなく「その候補を根拠から外す」**（両者が妥当と認めた）。
断定を減らす方向にしか働かない。ただし v1 の書き方には実害があるので修正（fable指摘）:

1. **作用範囲を「文」ではなく「節」にする。**
   日本語の指示は 「Aは触らないで、Bを直して」 のように1文に混在する。
   文単位で捨てると**Bへの正当な指示まで消える**。
   `、` `。` で分割した節のうち、一致した対象語を含む節だけを見る
1b. **節分割でも足りない場合は判定不能に倒す**（codex 2巡目指摘）。
   「**Aを触らずBを直す**」のように**1つの節に否定と複数の対象語が同居**すると、
   どちらに否定が掛かるか節分割では決まらない。日本語の係り受け解析は本修正の範囲外。
   規則: **節内に否定表現があり、対象語が2つ以上あるときは、その発話を根拠に使わず `判定不能`**。
   codex が1巡目に述べた「**解析不能なら判定不能**」をそのまま適用する。推測で当てにいかない
2. **「忘れないで」は肯定の指示**（「テスト追加を忘れないで」）。
   `ないで` で殺すと誤って落ちるので **`忘れないで` `欠かさないで` は否定語から除外する**
3. **抑制したことを reason に出す**（REQ-822/823 の思想＝無音の失敗を作らない）。
   「対象語に一致する発話はあったが否定表現を伴うため根拠に採用せず」と書く。
   汎用の「探索範囲内に検出できず」のままだと、
   **transcript に対象の話が出ているのにレビュアーには「指示なし」と見える**新しい無音の失敗になる

なお「Xを変更しないで」と言われて X を変更した場合、`unsolicited候補` になるのは**正しい**。
直すのは reason の文言であって結論ではない。

### テスト

1. 「〜は変更しないで」で `instructed=あり` にならない
2. 「Aは触らないで、Bを直して」で B への指示は生き残る
3. 「〜を忘れないで」は否定として扱わない
4. 否定で抑制したとき reason にその旨が出る
5. author が2番目の ref にいるとき、その窓の指示を検出できる
6. `index.ts` のような汎用語幹＋遠い1語では断定しない

## REQ-832 既知2件（汎用語1件での誤結合・仕様書の自己参照）

### 832-A 循環の除外

`hit.file === input.file` のとき `支持` にしない。
要求を書いている変更に「その要求が支持している」は循環。値は `判定不能`、reason に理由。

### 832-B 非明示一致の強化 — **fable案を採る**

v1では未定にしていた。前回 `>=2` にして既存テスト4件を壊した反省から、
**閾値ではなく「語の識別力」で決める**（fable案。codexも同方向）。

**仕様索引全体での段落頻度**を使う。`spec_index.tokens` から計算でき、新しい状態を持たない。

- **強い一致** = その語が出現する段落が少ない（例: ≤2段落、または全段落の≤10%）
- 規則: `支持` には **強い一致1件以上、または任意の一致2件以上**
- **次点との差**（codex 2巡目指摘・v2で落としていた）:
  **希少語であっても複数のREQに同程度で一致しうる**ので、頻度だけでは曖昧性を測れない。
  最上位候補と次点候補のスコア差が小さいときは **`判定不能`（曖昧）** に倒す。
  reason に「候補が複数あり絞れない」と出す

この案を採る理由（fable）:
- 観測された誤りを**機構として**潰す。「自動テスト」がREQ-202に誤結合したのは
  **その語がどこにでも出るから**で、頻度はまさにそれを直接測る指標
- **既存4テストを壊さないはず**。fixtureは1段落にしか出ない語（`payloadCache` 等）で
  紐づいており、単一一致で足りるまま。`>=2` が壊したのは、まさにその
  「一意な語」＝良いケースを罰したから
- 段落内近接は最も弱い。段落は空行区切りの小単位（spec/index.ts:57）なので
  段落内の距離はほぼノイズ

**手順の規律**: それでも**まず壊れた4テストの原因を特定する**。
fixtureが本当に一般語で紐づいているなら、閾値を合わせるのではなく
**テストの期待値の方を再評価する**（両者が指摘）。

### テスト

1. 循環（仕様書自身の変更）で `支持` にならない
2. 全段落に頻出する語1件だけでは `支持` にならない
3. 1段落にしか出ない語1件なら `支持` になる（既存fixtureが通り続けること）

## REQ-833 `derivePendingStatuses` が同一操作の完了行を巻き添えにする

### 症状（コードで確認済み）

```sql
UPDATE edit_events SET status='aborted' WHERE operation_id=?
```

主キーは `(operation_id, file)`。`AND file=?` も `AND status='pending'` も無い。
codex は複数ファイルを1操作で編集するため、**1ファイルが pending のまま24h経過すると

`WHERE operation_id=? AND file=? AND status='pending'`。`SELECT` 側で `file` も取る。

孤児 `edit_post` 1件が実行のたびに加算され、`rebuild` 後の値と食い違う。同ファイル・数行。

### テスト

1. 同一 operation_id で fileA=completed / fileB=pending。24h後に fileB だけ aborted、fileA は completed
2. 同じ ingest を2回実行しても `orphan_posts` が増えない
