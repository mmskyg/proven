# claim断定条件の厳格化 仕様書 v1.0

作成日: 2026-07-27
発端: claim受入計測（無作為50件・独立judge）で妥当率65%、基準80%に未達
設計レビュー: Codex（`instructed=なし` の廃止ほか）

---

## 1. 実測が示したこと

| claim | correct | incorrect | unsure |
|---|---|---|---|
| instructed=判定不能 | 6 | 0 | 0 |
| spec_support=判定不能 | 17 | 0 | 0 |
| instructed=あり | 0 | 2 | 0 |
| instructed=なし | 0 | 7 | 9 |
| spec_support=支持 | 3 | 5 | 1 |

**「判定不能」は23/23で正しく、壊れているのは断定している側**である。
断定27件のうち採点できたものだけで見ると precision は **3/17 = 18%**。
全体の65%という数字は、正しい判定不能が誤った断定を覆い隠した結果であり、報告として不適切だった。

## 2. 方針

検索で「関連しそうな証拠」を見つけたことと、その証拠が claim を**意味的に裏付ける**ことは別である。
断定には強い証拠を要求し、足りなければ `判定不能` とする。
ただし「探したが見つからなかった」という**観測**は捨てず、判定不能の理由として提示する。

## 3. 要求

REQ-701: **`instructed=なし` を自動claimとして出さない。**
一致が見つからない場合は `判定不能` とし、reason に「探索範囲内に明示指示を検出できず」と
探索範囲（セッション・発話数）を明示する。
理由: 「探して見つからなかった」は検索結果であり、「指示されていない」という否定命題ではない。
後者には探索範囲の完全性・境界の正しさ・言い換えや同意表現の解決が必要で、いずれも保証できない。
（人間が `confirm` で「なし」を確定する経路は残す。人間は業務文脈を含めて否定できる）

REQ-702: **探索範囲を「直近3発話」から「当該編集より前の同一セッションの全user発話」へ拡大する。**
直近性は候補の順位付けに使ってよいが、**否定の根拠には使わない**。
上限に達した場合は「上限超過のため判定不能」とし、上限到達を否定の証拠に変換しない。

REQ-703: **`instructed=あり` は、変更対象と要求された操作の双方が同一発話に現れる場合のみ**とする。
- 変更対象: ファイル名・パス・追加/削除行に含まれる固有識別子
- 汎用語（`user` `message` `type` `data` など、および言語の予約語）は**対象一致に数えない**
- ファイル名だけの一致では断定しない（同名ファイルが複数ある場合の誤りを防ぐ）

REQ-704: **`spec_support=支持` は、REQ段落の対象とhunkの対象が一致する場合のみ**とする。
関連語のFTSヒットは**候補の抽出にのみ使う**。
候補REQの段落本文に、hunkの固有識別子（ファイル名・シンボル）が現れない場合は `判定不能` とする。
一般的な不変条件（「既存テストが通ること」等）に技術名が含まれるだけの一致は支持としない。

REQ-705: 受入計測の集計を、単一の妥当率から**分けて出す**。
- 断定precision: 断定claim（あり/支持）のうち correct の割合
- 判定可能率(coverage): 全claimのうち断定できた割合
- 判定不能の妥当率: 判定不能claimのうち correct の割合
- 誤断定率: 全claimに占める「断定して間違えた」割合

受入基準（claim 80%）は**断定precisionに対して**適用する。
正しい判定不能で数字を膨らませない。

REQ-706: 上記は claim の**値の出し方**の変更であり、`instructed` / `spec_support` という
claim種別そのものは変更しない。lineage（帰属）にも影響させない。

## 4. 必須テスト

1. 直近3発話より前にある指示を検出できる（REQ-702）
2. 探索範囲に一致が無いとき `なし` ではなく `判定不能` になり、reasonに探索範囲が入る（REQ-701）
3. 汎用語だけの一致では `あり` にならない（REQ-703）
4. ファイル名だけの一致では `あり` にならない（REQ-703）
5. 対象と操作の双方が同一発話にあれば `あり` になる（REQ-703）
6. REQ段落にhunkの固有識別子が無ければ `支持` にならない（REQ-704）
7. REQ段落にhunkの対象が明記されていれば `支持` になる（REQ-704）
8. 集計が断定precision/coverage/判定不能妥当率/誤断定率を分けて出す（REQ-705）
9. 非退行: lineageの判定は変わらない（REQ-706）

## 5. 実測を受けた追加要求（2026-07-27）

REQ-701〜705 を実装して測り直したところ、断定7件が全て誤りだった。原因を分析して追加する。

REQ-707: `instructed` の観測（`no_match_in_scope`）は claim 値と分けて保持し、
`unsolicited候補` はその観測に基づく優先度シグナルとする（断定ではない）。

REQ-708: `eval --emit-cases --latest-only` を設ける。判定ロジックを変更した直後は、
旧ロジックで付いた過去の claim が母集団に混ざり、変更後の実力が測れないため。

REQ-709: **断定に使う対象語を「特徴的」なものに限定する。**
ASCII は6文字以上、日本語は4文字以上、かつ汎用語でないこと。
理由: 実測で「方が」「の組」「る場」のような日本語2-gramの断片が無関係な発話と一致し、
`instructed=あり` の誤断定を生んでいた。日本語は2-gramに加え、連続する4文字以上の語も対象語に持つ。

REQ-710: **変更行が REQ-ID を明示参照している場合は、その要求だけを見る。**
FTS の類似検索は別の要求を拾いうるため、明示参照があるときは検索結果を使わない。
参照先が仕様索引に存在しない、または候補仕様と一致しない場合は `判定不能` とし、
その旨を reason に出す（仕様に無いREQ-IDを参照しているコードを検出できる）。

REQ-711: **仕様書が変わっていたら ingest 時に索引を作り直す。**
`init` でしか索引を作らないため、仕様を更新しても古い索引で照合され、
「REQ-xxx が見つからない」という誤った理由が出ていた（ドッグフーディングで実際に発生）。

## 6. 3回の測定結果（2026-07-27）

同一の独立judge（Codex / gpt-5.6-sol）による、AI判定（unverified）の推移。

| | 断定件数 | 採点できた断定 | correct | 断定precision | 判定不能の誤り |
|---|---|---|---|---|---|
| 変更前 | 27 | 17 | 3 | 18% | 0 |
| REQ-701〜705 適用後 | 7 | 7 | 0 | 0% | 0 |
| REQ-709/710 適用後 | 1 | 1 | 0 | 0% | 0 |

**判定不能は3回とも一度も誤っていない**（合計 26 + 18 + 8 = 52件すべて correct または unsure）。

読み取れること:

1. 誤断定は着実に減った（14件 → 4件 → 1件）。ただし同時に**断定できる件数がほぼゼロになった**
2. つまり現状のヒューリスティックは「高precision・低coverage」ですらなく、
   **coverage がほぼ無い状態**である。受入基準（断定precision 80%）は**サンプル不足で測定不能**
3. `spec_support` は、変更行が REQ-ID を明示参照する運用（Proven 自身が推奨している運用）が
   徹底されていれば機能する見込みがある。実際、明示参照が仕様に存在しないケースを検出できた
4. `instructed` を語の一致だけで断定するのは、この規模の証拠では成立しない。
   Codex の助言どおり、ここから先は LLM 層（現在は既定OFF・未実装）の領域である

**結論: claim 側の受入基準達成には LLM 層の実装が前提になる可能性が高い。**
ヒューリスティックだけで到達できるのは「判定不能を正しく出す」ところまでである。
