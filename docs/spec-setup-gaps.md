# 設定の穴が静かに結果を劣化させる問題

2026-08-02 追加。実運用（別リポジトリ `notion_rag` での初導入）で見つかった4点。

共通する性質は「**失敗しないこと**」。どれもエラーにならず、既定値のまま最後まで動く。
その代わり影響は判定精度の低下として現れるので、利用者は劣化に気づけない。
Proven の思想（観測第一・断定しない・uncaptured を正直に出す）は「わからないことを隠さない」ことに
支えられているので、**設定由来の劣化も同じ扱いにする**。

## REQ-820 hookの登録先がcwd依存であることを明示する

`proven init` は既定でリポジトリの `.claude/settings.json` に hook を登録する。
しかし **Claude Code はセッション開始時の cwd の設定しか読まない**。
リポジトリ外（例: ホームディレクトリ）で起動したセッションからそのリポジトリを編集した場合、
hook は一度も発火せず、エラーも出ない。

これが最も危険なのは失敗が無音であることで、「捕捉0件」と「変更が無い」が見分けられない。
仕組み上の限界「hook外の変更は捕捉不可」の、最悪の発現形にあたる。

- 既定（リポジトリ内）で登録したときは、**cwdが一致するセッションでしか効かない**旨を必ず出す
- `proven init --global` でユーザー全体設定（`$CLAUDE_CONFIG_DIR` または `~/.claude/settings.json`）に
  登録できるようにする。この場合はどのディレクトリで起動しても捕捉される
- capture はもともと編集対象ファイルのパスからワークスペースを解決するので（REQ-230）、
  グローバル登録でも帰属は正しい。`.proven/` の無いリポジトリでの編集は no-op

## REQ-821 仕様書が1件も当たらないことを黙って通さない

既定の `spec_sources` は `docs/**/*.md` 固定。仕様書がリポジトリ直下にある構成では1件も当たらず、
その結果**全 hunk が `spec=判定不能`** になる。これは `unsolicited候補` のスコアに効くため、
設定ミスがそのまま偽陽性の増加として現れる。

`init` の警告は従来「REQ-xxx形式のIDが見つかりません」だけで、
**置き場が違う**のか**IDを振っていない**のかを区別していなかった。原因も対処も違うので分ける。

- 対象ファイル0件 → 検索パターンを示し、`spec_sources` を直すよう促す
- 対象ファイルはあるがREQ-IDが0件 → 従来どおりIDを振る運用を勧める

## REQ-822 exclude件数にProven自身を数えない

`.proven/config.yaml` は共有したい設定なので `.gitignore` に入れない＝ `git ls-files` に載る。
一方 `excludedByCapture` は `.proven/` 以下を強制除外するため、
`ingest` のたびに `exclude対象1件は追跡外です` が出る。

これは**全リポジトリで永久に出続け、利用者に対処のしようがない**警告で、
しかも件数だけでファイル名が出ないため確認もできない。警告そのものの価値を下げる。

`capture.exclude` で**利用者が意図的に外したもの**だけを数える。

## REQ-823 決めていない設定のまま進もうとしたら警告する

既定値が入っているので動くが、「動く」と「決めた」は違う。
未決のまま進んだ場合の影響は失敗ではなく判定精度の低下なので、放置すると気づけない。
`init`（設定時）と `precheck`（レビューを頼む直前）で、未決を**決め方つきで**読み上げる。

検出する未決とその影響:

| key | 未決だと何が起きるか |
|---|---|
| `reviewer_id` | finding・attest の確認者が空になり、後から「誰が見たのか」を辿れない |
| `spec_sources` | 全変更が `spec=判定不能` になり、頼んでいない変更の判定が甘くなる |

| `policy` | precheck が既定の検査しか行わず、プロジェクト固有の禁止設計が素通りする |
| `triage.boundary_paths` | 認証・課金・マイグレーション等の重要な変更が些末な変更と同列に並ぶ |

**止めない。警告のみ。** 未決を理由にレビュー依頼を塞ぐと、決めるまで作業できなくなり、
「とりあえず埋める」を誘発して決定の質が下がるため。判断は人間に残す。

各項目は「何が決まっていないか」「このまま進むと何が起きるか」「どう決めるか」の3点を必ず持つ。
決め方の書いていない警告は無視されるだけなので、`howTo` は必須とする。

## REQ-824 後から書いた仕様書を「事前の根拠」に数えない

REQ-820〜823 を実装した後で本ファイルを追加したところ、**同じ変更集合のまま
unsolicited候補が11件→0件**になった。仕様書がコードより後に書かれたことは
何も検証されていないので、これは「ズレていなかった証明」にはならない。

つまり現状の `spec_support` には、**実装を終えてから仕様書を足せば、自分がやったことを
何でも「仕様に沿っている」に変えられる**という抜け穴がある。
Proven は「レビューの認知負荷を下げる」ためのものなので、
後付けの正当化を通してしまうと、通した分だけレビュアーを欺くことになる。

`spec_support` に値 `事後` を追加して `支持` と区別する。

- 判定は**捕捉済み編集イベントの時刻のみ**で行う(観測第一)。
  仕様書ファイルの初回編集が、**この変更を作った編集**より後なら `事後`
- どちらかが捕捉されていなければ `null` として**断定しない**。
  この場合は `支持` のままとし、reason に「作成時期は未観測」と明記する
- 判定は段落単位ではなくファイル単位。段落の作成時刻を保持していないための近似であり、
  **既存の仕様書へ今回追記した場合は「先にあった」と緩い側に倒す**
- `事後` は necessity の essential 条件を満たさない。
  つまり **unsolicited候補 のまま残る**。これが本要求の目的
- unsolicited の理由文には「仕様書はあるがコードより後に書かれており事前の根拠にならない」と出す。
  利用者から見れば仕様書は存在するので、単に「支持なし」とだけ言うと理由が分からない

正しい運用は「実装より先に仕様書を書く」で、これは元々チーム利用時の合意事項(3)に挙げてある。
本要求はそれを**強制はしないが、守らなかったことが記録に残る**ようにするもの。

## REQ-826 事後判定の比較対象を「この変更を作った編集」に限る

REQ-824 の初版は、hunk に紐づく編集イベント全ての最小時刻とコードを比べていた。
これには**位置が重なるだけの編集(`refSupport=touched`)**が含まれるため、
README のように何度も触るファイルでは「そのファイルを最初に触った時刻」まで遡ってしまい、
**仕様書より後に書いた行なのに事後と誤判定**する。

実測(2026-08-03、現行ロジック22件)で、`spec=事後` の誤判定が3件出た。
誤り6件のうち半分がこれで、正解率 72.7% を押し下げていた。

比較対象を `refSupport=author`(その変更を実際に作った編集)に限る。
author が特定できない場合(refSupport 未算出・touched のみ)は **`null` にして断定しない**。
「この変更を作った編集」が分からない以上、前後関係も言えないため。

### 「使わないと決めた」を表明できるようにする

`spec_sources: []` を「仕様書を使わないと決めた」表明として扱い、未決から外す。

小さなリポジトリでは仕様書を置かない選択が普通にあり、そこで消しようのない未決警告を出し続けると、
REQ-822 で潰したのと同じ**対処のしようがない警告**を別の形で作ることになる。
既定値のまま(`docs/**/*.md`)で1件も当たらない場合だけ「実態と合っていない」として警告する。
