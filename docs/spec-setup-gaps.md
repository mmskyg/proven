# 設定の穴が静かに結果を劣化させる問題

2026-08-02 追加。実運用（別リポジトリ `notion_rag` での初導入）で見つかった4点。

共通する性質は「**失敗しないこと**」。どれもエラーにならず、既定値のまま最後まで動く。
その代わり影響は判定精度の低下として現れるので、利用者は劣化に気づけない。
Proven の思想（観測第一・断定しない・uncaptured を正直に出す）は「わからないことを隠さない」ことに
支えられているので、**設定由来の劣化も同じ扱いにする**。

## REQ-820 hookの登録先がcwd依存であることを明示する

`proven init` は既定でリポジトリの `.claude/settings.json` に hook を登録する。
しかし **Claude Code はセッション開始時の cwd の設定しか読まない**。
リポジトリ外（例: ホームディレクトリ）で起動したセッションからそのリポジトリを編集した場合、
hook は一度も発火せず、エラーも出ない。

これが最も危険なのは失敗が無音であることで、「捕捉0件」と「変更が無い」が見分けられない。
仕組み上の限界「hook外の変更は捕捉不可」の、最悪の発現形にあたる。

- 既定（リポジトリ内）で登録したときは、**cwdが一致するセッションでしか効かない**旨を必ず出す
- `proven init --global` でユーザー全体設定（`$CLAUDE_CONFIG_DIR` または `~/.claude/settings.json`）に
  登録できるようにする。この場合はどのディレクトリで起動しても捕捉される
- capture はもともと編集対象ファイルのパスからワークスペースを解決するので（REQ-230）、
  グローバル登録でも帰属は正しい。`.proven/` の無いリポジトリでの編集は no-op

## REQ-821 仕様書が1件も当たらないことを黙って通さない

既定の `spec_sources` は `docs/**/*.md` 固定。仕様書がリポジトリ直下にある構成では1件も当たらず、
その結果**全 hunk が `spec=判定不能`** になる。これは `unsolicited候補` のスコアに効くため、
設定ミスがそのまま偽陽性の増加として現れる。

`init` の警告は従来「REQ-xxx形式のIDが見つかりません」だけで、
**置き場が違う**のか**IDを振っていない**のかを区別していなかった。原因も対処も違うので分ける。

- 対象ファイル0件 → 検索パターンを示し、`spec_sources` を直すよう促す
- 対象ファイルはあるがREQ-IDが0件 → 従来どおりIDを振る運用を勧める

## REQ-822 exclude件数にProven自身を数えない

`.proven/config.yaml` は共有したい設定なので `.gitignore` に入れない＝ `git ls-files` に載る。
一方 `excludedByCapture` は `.proven/` 以下を強制除外するため、
`ingest` のたびに `exclude対象1件は追跡外です` が出る。

これは**全リポジトリで永久に出続け、利用者に対処のしようがない**警告で、
しかも件数だけでファイル名が出ないため確認もできない。警告そのものの価値を下げる。

`capture.exclude` で**利用者が意図的に外したもの**だけを数える。

## REQ-823 決めていない設定のまま進もうとしたら警告する

既定値が入っているので動くが、「動く」と「決めた」は違う。
未決のまま進んだ場合の影響は失敗ではなく判定精度の低下なので、放置すると気づけない。
`init`（設定時）と `precheck`（レビューを頼む直前）で、未決を**決め方つきで**読み上げる。

検出する未決とその影響:

| key | 未決だと何が起きるか |
|---|---|
| `reviewer_id` | finding・attest の確認者が空になり、後から「誰が見たのか」を辿れない |
| `spec_sources` | 全変更が `spec=判定不能` になり、頼んでいない変更の判定が甘くなる |

| `policy` | precheck が既定の検査しか行わず、プロジェクト固有の禁止設計が素通りする |
| `triage.boundary_paths` | 認証・課金・マイグレーション等の重要な変更が些末な変更と同列に並ぶ |

**止めない。警告のみ。** 未決を理由にレビュー依頼を塞ぐと、決めるまで作業できなくなり、
「とりあえず埋める」を誘発して決定の質が下がるため。判断は人間に残す。

各項目は「何が決まっていないか」「このまま進むと何が起きるか」「どう決めるか」の3点を必ず持つ。
決め方の書いていない警告は無視されるだけなので、`howTo` は必須とする。

## REQ-824 後から書いた仕様書を「事前の根拠」に数えない

REQ-820〜823 を実装した後で本ファイルを追加したところ、**同じ変更集合のまま
unsolicited候補が11件→0件**になった。仕様書がコードより後に書かれたことは
何も検証されていないので、これは「ズレていなかった証明」にはならない。

つまり現状の `spec_support` には、**実装を終えてから仕様書を足せば、自分がやったことを
何でも「仕様に沿っている」に変えられる**という抜け穴がある。
Proven は「レビューの認知負荷を下げる」ためのものなので、
後付けの正当化を通してしまうと、通した分だけレビュアーを欺くことになる。

`spec_support` に値 `事後` を追加して `支持` と区別する。

- 判定は**捕捉済み編集イベントの時刻のみ**で行う(観測第一)。
  仕様書ファイルの初回編集が、**この変更を作った編集**より後なら `事後`
- どちらかが捕捉されていなければ `null` として**断定しない**。
  この場合は `支持` のままとし、reason に「作成時期は未観測」と明記する
- 判定は段落単位ではなくファイル単位。段落の作成時刻を保持していないための近似であり、
  **既存の仕様書へ今回追記した場合は「先にあった」と緩い側に倒す**
- `事後` は necessity の essential 条件を満たさない。
  つまり **unsolicited候補 のまま残る**。これが本要求の目的
- unsolicited の理由文には「仕様書はあるがコードより後に書かれており事前の根拠にならない」と出す。
  利用者から見れば仕様書は存在するので、単に「支持なし」とだけ言うと理由が分からない

正しい運用は「実装より先に仕様書を書く」で、これは元々チーム利用時の合意事項(3)に挙げてある。
本要求はそれを**強制はしないが、守らなかったことが記録に残る**ようにするもの。

## REQ-826 事後判定の比較対象を「この変更を作った編集」に限る

REQ-824 の初版は、hunk に紐づく編集イベント全ての最小時刻とコードを比べていた。
これには**位置が重なるだけの編集(`refSupport=touched`)**が含まれるため、
README のように何度も触るファイルでは「そのファイルを最初に触った時刻」まで遡ってしまい、
**仕様書より後に書いた行なのに事後と誤判定**する。

実測(2026-08-03、現行ロジック22件)で、`spec=事後` の誤判定が3件出た。
誤り6件のうち半分がこれで、正解率 72.7% を押し下げていた。

比較対象を `refSupport=author`(その変更を実際に作った編集)に限る。
author が特定できない場合(refSupport 未算出・touched のみ)は **`null` にして断定しない**。
「この変更を作った編集」が分からない以上、前後関係も言えないため。

## REQ-827 role=user でも「人が言ったこと」でない行は指示に数えない

Claude Code の transcript は、**コンパクション要約**と**スラッシュコマンドの実行・標準出力**も
`role=user` として書き込む。とくにコンパクション要約は会話全体の技術用語
(ファイル名・識別子・SQL断片)を大量に含むため、これを発話として扱うと
**ほぼ何にでも一致し**、指示が無い変更まで `instructed=あり` になる。

実測(2026-08-03)で、`sqlite / database / filter` のような語で一致した
`instructed=あり` の誤検出が出た。該当する発話は実在せず、
すべて1本のコンパクション要約(transcript の同一行)に由来していた。

除外するもの:

- `isCompactSummary === true` の行
- `<command-name>` / `<local-command-stdout>` / `<local-command-stderr>` を含む行

**`isMeta` では弾かない。** Discord等のチャネル経由で届いた**本物のユーザー発話にも
`isMeta` が付く**ため、弾くと指示が丸ごと見えなくなる(実測: 対象セッションの
ユーザー発話40件がすべてチャネル経由)。

## REQ-830 判定対象は「ファイルの存在」ではなく「要求の存在」

REQ-824/826 は仕様書**ファイル**の編集時刻で前後を見ていた。しかし
**ファイルが前から在っても、支持根拠の段落を今日書いたなら事後**である。
時刻の比較をやめ、**その時点の内容を復元して要求が載っていたか**で判定する。

安全性は非対称性に依る:
- ある時点 ≥ T で**不在**が観測された → T より後に追加された、と言い切れる(`事後` は堅い)
- ある時点 U > T で**存在**が観測された → T 時点の存在は証明しない → 緩い側(`支持`)へ倒す

T = author編集の `MIN(ts_pre)`。検索は **completed のみ**。
作成時の編集が `aborted` だと2番目が最古に見えるが緩い側へ倒れるだけなので許容する。
**これは仕様であり「バグ」として直さないこと。**

- **c-1**: `V < T` での不在は T 時点の不在を証明しない。`(V, T]` に捕捉外の編集がありうる。
  次の捕捉編集 W について `pre(W) == result(V)`(W が無ければ head の内容と比較)なら
  その区間は無変更 → `事後` 妥当。一致しなければ **`null`(断定しない)**。
  厳密にはこれは**両端の一致**であって区間内が不変だった証明ではない。
  捕捉外で足して W より前に戻せば擦り抜けるが、
  **意図的な「捕捉外での追加→復元」はこのツールのあらゆる機構を無効化する**ので限界として扱う
- **c-2**: 仕様書の編集がコードの author 編集と `operation_id` を共有する、または `ts_pre` が並ぶ場合は
  `支持` 側へ倒す。1操作で複数ファイルを編集するハーネスでは行間のサブミリ秒順序は事実上任意
- **c-3**: 過去内容の検査は REQ-ID だけでなく、非明示経路では一致語も要求する。
  ただし**既存REQを自分の変更に合わせて書き換える**回避は明示参照経路では防げない(限界)
- 前後関係が未観測のときは値を `支持` のまま残し **confidence を 0.5 → 0.4** に下げる。
  内容の対応は観測できており、**観測されていない反証は反証の証拠にならない**ため。
  reason で3原因(author不明 / 仕様書の編集が未捕捉 / 決定的な区間に捕捉外の変更)を区別する。
  **この文言は「意味的一致」と「時間的先行性」を1つのclaimで運ぶ役割を担っているので、安定させること**
- candidate / broken 帰属の上に前後判定を載せない(REQ-411 と揃える)

**限界(文書化)**: ヒアドキュメント等 hook 外で仕様書を作ってから capture 下で編集すると、
最古の捕捉編集の pre が非NULL になり緩い側へ倒れる。「hook外は捕捉不可」がここに現れたもの。

## REQ-834 サブエージェント/チームメイトの発言を人の指示に数えない

REQ-827 の続き。`<teammate-message>`(他エージェントからのレビュー文)と
サブエージェントのプロンプト(`isSidechain`)も `role=user` で届く。
これらは**機械が書いた文でファイル名と識別子が密に並ぶ**ため、
コンパクション要約と同じく「ほぼ何にでも一致する」誤検出源になる。

REQ-827 の時点では「要検証」として保留していたが、
**実測で確認された**: fable のレビュー文1本が `buffer` `statSync` `isFile`
`commit` `manifest` `entries` 等で複数の hunk に `instructed=あり` を付けていた。
REQ-831-B で全 linkedEvents の窓を探索するようにしたことで露出が広がった。

## REQ-832 仕様一致は「語の識別力」で判定する / 循環参照を支持にしない

- **A**: `hit.file === input.file` のとき `支持` にしない。
  要求を書いている変更に「その要求が支持している」は循環で根拠にならない
- **B**: 明示参照でない一致は**閾値ではなく語の識別力**で決める。
  一致語1件で足りると「自動テスト」「sessionref」のようにどこにでも出る語で誤結合する
  （実測でREQ-202・REQ-219への誤結合が出た）。
  - **強い一致** = その語が出現する段落が少ない（≤2段落、または全段落の≤10%）
  - `支持` には**強い一致1件以上、または任意の一致2件以上**
  - 段落頻度は `spec_index` から計算し、新しい状態を持たない。
    **`tokens` 列はトークン列であって原文ではない**（日本語は2-gram）ので、
    検索語も同じ `tokenize` を通してから照合する。
    生の部分文字列で照合すると**日本語の語が常に0件になる**
  - **次点との差**: 希少語でも複数のREQに同程度で一致しうる。
    最上位と次点のスコア差が小さいときは `判定不能`（曖昧）に倒す

以前「一致2件以上」という閾値にしたところ既存テストが4件壊れた。
原因は**一意な語＝良いケースを罰していた**ことで、識別力ベースなら壊れない
（実際、本実装では4件とも通ったまま）。**閾値を期待値に合わせるのではなく、
機構で潰す**というのがこの要求の趣旨。

## REQ-831 指示判定を「対象語の一致数」だけで決めない

- **A**: ファイル名の脚にも `isDistinctiveTarget` を課す。`index.ts` `utils.ts` の語幹は汎用語で、
  `containsToken` は4文字以上の部分一致を許すためほぼ任意の発話に当たる。
  拡張子つき basename(`parser.ts`)は残るので強い信号は維持される
- **B**: 会話窓を `linkedEvents[0]` に固定しない。`refs` の順序は span 挿入順なので、
  先頭が `touched`(位置が重なっただけ)で真の author が後ろにいることがある。
  **author を優先し、全 linkedEvents の窓を探索**する
- **C**: 否定表現を伴う候補は**根拠から外す**。断定条件に否定検査を足すのではないので、
  **断定を減らす方向にしか働かない**
  - 作用範囲は文ではなく**節**(`、`『。』で分割)。「Aは触らないで、Bを直して」で B への指示を殺さないため
  - `忘れないで` `欠かさないで` は肯定の指示なので否定語から除く
  - **1つの節に否定と対象語が2つ以上あるときは、その発話を使わず判定不能**。
    「Aを触らずBを直す」の係り受けは節分割では決まらず、日本語の係り受け解析は範囲外。
    **解析不能なら判定不能**に倒す
  - 抑制したときは reason にその旨を出す。汎用の「検出できず」のままだと、
    transcript に対象の話が出ているのにレビュアーには「指示なし」と見える＝新しい無音の失敗になる

なお「Xを変更しないで」と言われて X を変更した場合、`unsolicited候補` になるのは**正しい**。
直すのは reason の文言であって結論ではない。

## REQ-829 non-ASCII ファイル名を黙って落とさない

`git ls-files` / `git ls-tree` は既定(`core.quotepath=true`)で non-ASCII パスを
octal-quote して返す。この引用符付き文字列をパスとして扱うと `fs.existsSync` が false になり、
**日本語名のファイルが警告も無く manifest から消える**。編集してもレビュー対象に現れず、
「捕捉0件」と「変更なし」が区別できない ＝ REQ-820 が警告した無音の失敗そのもの。

- git 呼び出しに `-c core.quotepath=off` を付ける。
  `-z` は出力パーサの書き換えが必要なため採らない。**改行入りファイル名は依然として扱えない**
- 読めなかったパスは捨てずに集め、**ファイル名つきで警告に出す**。
  パス破損・権限・競合削除のいずれでも無音にならないようにする
- commit revision 側も per-file の `cat-file` 失敗で ingest 全体を落とさない
- `commitHeadRefOrEmpty` の握りつぶしを廃止。失敗理由を持ち帰り警告に出す。
  以前は revision 構築の実バグが「対象なし(差分がありません)」に化けていた

**移行時の注意**: 修正後の初回 ingest は、これらのファイルを含まない旧 head manifest との差分になるため、
**ファイル全体の追加 hunk として大量に出る**。回帰ではない。`input_digest` も変わるので dedupe されない。

## REQ-833 pending 中断が同一操作の完了行を巻き添えにしない

`derivePendingStatuses` の UPDATE が `WHERE operation_id=?` のみで、
主キー `(operation_id, file)` のうち file を絞っていなかった。
1操作で複数ファイルを編集するハーネス(codex の `apply_patch`)では、
**1ファイルが pending のまま24h経過すると同じ操作の completed 行まで aborted になる**。
ingest は completed しか読まないため、そのファイルの来歴が黙って消える。

`WHERE operation_id=? AND file=? AND status='pending'` にする。

あわせて孤児 post の二重計上を修正する。ingest は毎回 edits.jsonl を全再適用するため、
pre の無い post 1件が実行のたびに加算され、`rebuild` 後の値と食い違っていた。

### 「使わないと決めた」を表明できるようにする

`spec_sources: []` を「仕様書を使わないと決めた」表明として扱い、未決から外す。

小さなリポジトリでは仕様書を置かない選択が普通にあり、そこで消しようのない未決警告を出し続けると、
REQ-822 で潰したのと同じ**対処のしようがない警告**を別の形で作ることになる。
既定値のまま(`docs/**/*.md`)で1件も当たらない場合だけ「実態と合っていない」として警告する。
