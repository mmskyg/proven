# 受入計測の証拠強化と合否閾値 仕様書 v1.0

作成日: 2026-07-26

## 背景（実測で判明した問題）

`proven eval lineage --emit-cases --sample 50` で生成したケースを独立judge（Codex）に判定させたところ、
**50件中49件が `unsure`（証拠不足で判定できない）** となった。judgeの理由は一貫して
「引用はhook確認や実測の話ばかりで、この変更を当該イベントが作った証拠になっていない」。

原因を調べたところ:

- 証拠に含まれる transcript 引用は **assistant発話91件に対しuser発話2件**
- **50件中19件は引用ゼロ**
- そして根本的に、**帰属判定は会話ではなく blobチェーン（編集前後の内容ハッシュの連鎖）で行っている**のに、
  その機械的証拠がケースに入っていない

つまり「判定に使った本当の根拠」を提示しないまま判定を求めていた。第三者は検証しようがない。

もう1つ、集計が **人間確認1件で `受入基準(lineage 90%): PASS`** を出した。n=1でのPASSは誤解を招く。

## 要求

REQ-301: lineage評価ケースの証拠に、帰属判定が実際に用いている**機械的証拠**を含める。

REQ-302: 帰属された各編集イベントについて、次を提示する。

```
attribution_basis: {
  pre_blob:  "<hash先頭12桁>",      // 編集前の内容ハッシュ
  post_blob: "<hash先頭12桁>",      // 編集後の内容ハッシュ
  event_diff: "<このイベント自身が作った差分(先頭N行)>",
  introduced_lines: ["+..."],       // このイベントで現れた行のうち、hunkの追加行と一致するもの
  removed_lines:    ["-..."],       // このイベントで消えた行のうち、hunkの削除行と一致するもの
  overlap: "full" | "partial" | "none"   // hunkの変更行をこのイベントがどれだけ説明できるか
}
```

REQ-303: 対照として、**同ファイルの非帰属イベントにも同じ機械的証拠**を付ける。
「別のイベントの方がこの変更を説明できてしまう」ケースを judge が見抜けるようにするため。

REQ-304: rubric を更新し、**機械的証拠を主・会話引用を補助**として扱うことを明示する。
会話引用が無いこと自体は `unsure` の理由にならない（帰属判定は会話に依存しないため）。

REQ-305: 受入合否は**最低サンプル数**（既定20件）を満たすまで PASS を出さない。
満たない場合は「判定不能(サンプル不足 n/20)」と表示する。FAIL の表示は閾値未満なら
サンプル数に関わらず出してよい（少数でも基準割れは事実として報告する）。

REQ-306: 上記は表示と証拠の追加のみで、**帰属判定のロジック自体は変更しない**。
既存の判定結果・イベント形式は不変とする。

## 受入条件

1. 既存テストが全て通る
2. lineageケースに `attribution_basis` が入り、`overlap` が算出される
3. 人間確認が20件未満のとき PASS を出さない（テストで固定）
4. 同ファイルの非帰属イベントにも機械的証拠が付く

## 実装後の測定結果（2026-07-26）

同じ独立judge（Codex / gpt-5.6-sol）に、同種の母集団を判定させた結果:

| | correct | unsure | incorrect |
|---|---|---|---|
| 改善前 | 1 | 49 | 0 |
| 改善後 | 35 | 12 | 3 |

判定できた割合が 1/50 → 38/50 になった。AI判定（unverified）での正解率は 92.1%（35/38）。
合否表示も `PASS`（n=1）から `判定不能(サンプル不足 1/20件)` に変わり、REQ-305 が意図どおり働いている。

## この測定で見つかった未解決の問題（REQ-307 候補）

judge が `incorrect` とした3件は、いずれも次の形だった:

> hunk は `uncaptured`（hook外の変更）と表示されているが、捕捉済みイベントが
> `overlap: partial` でその hunk の変更行を実際に作っている。

実際に `src/cli/init.ts` のケースを確認したところ、事実だった。原因は帰属が**行スパンの追跡**で
行われているため。途中の編集が記録されていないと行の対応が切れ、内容的には捕捉済みイベントが
作った行であっても、どのイベントスパンとも交差せず `uncaptured` に落ちる（`attributeHunk`）。

`uncaptured` は「AIの記録が存在しない」と読めるため、**記録は存在するが連鎖が切れている**ケースを
これで表すのは誤解を招く。既存の `broken`（捕捉済みだが連鎖が切れている）に寄せるのが筋だが、
判定条件の変更は帰属ロジックそのものの変更になるため、本仕様のスコープ外とする。

**未解決として記録する。**

### 設計レビュー（Codex に相談・2026-07-26）

「`broken` に寄せる」案は**否決**された。要旨:

- `broken` は「追跡していたイベントspanがgapに潰された」という具体的な意味を既に持つ。
  内容一致しかないケースを同じ箱に入れると**証拠の種類が失われる**。新状態 `candidate` を推奨。
- 行集合の一致は**候補抽出には妥当だが、帰属確定には不十分**。
  偶然一致（`}` `return null;`）、formatterの削除・再追加、
  **AIが作った行をgapが消し別の主体が同じ文字列を再追加**するケースがある。
- confidence は構造的 `broken`(0.4) **以下**に置くべき。`linked`(1.0) との中間(0.7等)は
  「構造的brokenより確か」と誤読されるが根拠がない。
- 思想との整合は「観測事実 / 判定 / 推定」の3層に分けて提示すれば取れる。
  反するのは**一致を帰属の事実として表示すること**。

## 段階A: 過剰断定の除去（実装済み）

上記レビューで、**先に入れた REQ-301〜304 自体に過剰断定があった**ことが判明したため先に直す。

REQ-308: rubric から「`overlap` が full/partial なら、そのイベントが変更行を実際に作ったことを意味する」を削除する。
`overlap` は「同じ文字列の変更行がイベント差分にも存在する」までしか意味しない。
`attribution_basis.overlap_note` にもこの限定を明記する。

REQ-309: `attributionBasis` の突き合わせを**符号付き・多重度保存**にする。
`Set` 比較では、hunk側に同じ行が2回出ても1回の一致で `full` になってしまう。
併せて、一致行のうち情報量のあるものの数を `informative_matches` として出す
（`}` `return null;` のような予約語のみの定型行は単独では証拠にしない）。

REQ-310: `ask` の uncaptured 表示から断定を外す。
「この変更はhook捕捉外で発生しました」→「この変更に対応する捕捉イベントを確認できません。
hook外の変更か、途中の編集が記録されず連鎖が切れた可能性があります」。

## 段階B: `candidate` 状態の導入（未着手）

内容一致による候補提示。誤検出ガード（同一ファイル / completed / 時系列整合 / 連続一致 /
情報量 / 競合時は ambiguous）、confidence 上限 0.4、Codex が挙げた敵対的テスト群が前提。
帰属ロジックの変更を伴うため、着手前に別途仕様を書く。

## 段階C: claim側の証拠強化（2026-07-26）

claim の受入計測に着手する前に、ケースの証拠を点検したところ2つの欠陥が見つかった。
lineage 側と同じ轍（証拠不足のまま測って `unsure` の山を作る）を踏まないよう先に直す。

REQ-601: **`spec_excerpt` が仕様本文ではなくトークン列になっている。**
`spec_index` はトークン列とハッシュしか保持しておらず、証拠として
`"req 既存 存の の自 自動 動テ テス スト..."`（日本語2-gramの羅列）が出ていた。判定者には読めない。
仕様ファイルの該当段落を読み直して**実際の本文**を提示する。

REQ-602: **`判定不能` のケースに判断材料が無い。**
`claim_evidence` が空で、`tool_reason`（例: 「編集イベントが捕捉されていないため会話と照合できない」）
しか出ない。判定者は「本当に捕捉されていないのか」を確認できない。
hunk の捕捉状態・transcript の可読性・仕様索引の有無を `context` として同梱する。

REQ-603: `instructed` のケースには、一致した語だけでなく**発話の引用文**を含める。

REQ-604: `hunk_diff` は先頭40行で打ち切る（新規ファイル追加で数百行になり、証拠が埋もれるため）。

REQ-605: 上記は証拠の提示のみで、**claim 判定ロジックは変更しない**。
