# 帰属状態 `candidate` の導入 仕様書 v1.0

作成日: 2026-07-26
前提: `docs/spec-eval-evidence.md` §「この測定で見つかった未解決の問題」および Codex への設計相談

---

## 1. 解く問題

現在 `attributeHunk` は、捕捉イベントの**行スパン**が hunk と交差するかだけで判定している。

| 条件 | 現在の結果 |
|---|---|
| 汚染されていないスパンが交差 | `linked`(confidence 1.0) |
| gap に汚染されたスパンが交差 | `broken`(confidence 0.4) |
| 交差するスパンが1つも無い | **`uncaptured`(confidence null)** |

このため、**途中の編集が記録されず行の対応が切れた**場合、内容的には捕捉済みイベントが作った行でも
`uncaptured` に落ちる。`uncaptured` は利用者に「AIの記録が存在しない=人間の手編集」と読まれるため、
レビュアーの判断（精読すべきか、誰に聞くべきか）を誤らせる。

実際に本リポジトリの `src/cli/init.ts` で、捕捉イベント `op_init_agents` の差分に hunk の追加行と
完全一致する行が含まれているのに `uncaptured` と表示されるケースを確認した。

## 2. 方針

**`broken` に寄せない。** `broken` は「追跡していたスパンが gap に潰された」という具体的な意味を既に持つ。
内容一致しかないケースを同じ箱に入れると証拠の種類が失われる。新しい状態 `candidate` を追加する。

REQ-401: `lineage_status` に `candidate` を追加する。意味は
**「捕捉イベントに内容上の対応候補があるが、連鎖が切れているため帰属は確定できない」**。
`edit_capture_status` は `captured`（イベント自体は捕捉されている、という観測事実）とする。

| 状態 | edit_capture | lineage | 意味 |
|---|---|---|---|
| スパンで追跡可能 | captured | linked | 確定リンク |
| スパンが gap に汚染 | captured | broken | 構造的リンクあり・連鎖に欠損 |
| 連鎖断絶＋内容一致 | captured | **candidate** | **候補のみ。確定ではない** |
| 対応候補なし | uncaptured | （なし） | 対応する捕捉イベントを確認できない |

REQ-402: `candidate` の refs は「帰属イベント」ではなく**候補イベント**として扱う。
`method` は `blob-chain` ではなく **`content-match`** を記録し、証拠の種類を判別できるようにする。

## 3. 候補検出（誤検出ガード）

REQ-403: 候補判定は**符号付き・多重度保存**で行う。追加行は追加行と、削除行は削除行とだけ突き合わせる。
`Set` 比較は同じ行の複数出現を1回の一致で埋めてしまうため使わない。

REQ-404: 一致行のうち**情報量のある行のみ**を証拠として数える。
予約語のみで構成される定型行（`}` / `return null;` / `else {` 等）、記号のみの行、8文字未満の行は
単独では証拠にしない（判定は `isInformativeLine`）。

REQ-405: 候補として採るのは次のいずれかを満たす場合に限る。

1. **連続する情報量のある追加行が2行以上**、hunk とイベント差分の双方で同じ順序で一致する
2. **特徴的な1行**（40文字以上、または長い文字列リテラルを含む）が一致する

いずれも満たさない場合は候補にせず、従来どおり `uncaptured` とする。

REQ-406: 対象イベントは次に限る。
- 同一ファイルの `completed` イベント
- pre/post のスナップショットが復元できるもの
- 当該 ingest の base→head 区間に属するもの（区間外の古い/新しいイベントは除外）

REQ-407: 候補が複数あり最良スコアが同点の場合、**1つに絞らない**。
全候補を refs に入れ、`ambiguous` として扱い、confidence を上げない。

REQ-408: 巨大なイベントほど偶然一致しやすいため、
イベント全体の変更行数に対する一致行数の比が低い場合はスコアを下げる。

## 4. confidence

REQ-409: `candidate` の confidence は **0.4 を上限**とし、構造的な `broken`(0.4) を超えない。
`linked`(1.0) と `broken`(0.4) の中間（0.7 等）には置かない。
内容一致だけでは「構造的 broken より確か」と言える根拠がないため。

| 条件 | confidence |
|---|---|
| 特徴的な1行のみ一致 | 0.2 |
| 情報量のある連続2行以上が一致 | 0.3 |
| 追加側・削除側の双方が一致 | +0.1（上限 0.4） |
| 候補が複数で同点（ambiguous） | 0.2 を上限 |
| 巨大イベントで一致比が低い | −0.1（下限 0.1） |

## 5. 提示（思想との整合）

REQ-410: `candidate` は**観測事実 / 判定 / 推定**を分けて提示する。「このイベントが作った」と断定しない。

```
帰属は判定不能(連鎖断絶)。捕捉イベント op_xxx に同一内容の候補があります。
特徴的な追加3行が順序付きで一致、他の候補なし。推定 confidence: 0.3
```

REQ-411: 下流は `candidate` を `linked` として扱わない。かつ `uncaptured` としても扱わない。

- `triage`: `no-lineage` 加点（25点）の対象に含める（帰属が確定していないため精読対象）。
  ただし表示は `uncaptured` と区別する
- `ask`: 「hook外で発生した」と表示しない。候補として提示する
- `ingest` の集計: `linked` にも `uncaptured` にも数えず、`candidate` として内訳を出す
- `eval`: `candidate` を `linked` と同一視しない

REQ-412: 既存の `linked` / `broken` / `uncaptured` の判定条件は変更しない。
`candidate` は「従来 `uncaptured` になっていたもの」の一部だけを引き取る。

## 6. 必須テスト（敵対的ケース中心）

期待値は実装アルゴリズムではなく、**誰がどの変更をしたかというシナリオ上の事実**から決める。

### 正例
1. 再現ケース: 捕捉イベントが特徴的な複数行を追加 → 未捕捉の中間編集で対応が切れる →
   最終 hunk にその行が残る → `uncaptured` ではなく `candidate`、refs は候補、`linked` にしない
2. 追加・削除の双方が対応 → 単純な追加一致より高い confidence（ただし 0.4 以下）
3. 特徴的な1行のみ → `candidate` かつ confidence 0.2

### 敵対的負例
4. `}` だけの一致 → 候補にしない
5. `return null;` だけの一致 → 候補にしない
6. 定型2行（`if (...) {` + `return null;`）→ 「2行以上」だけでは候補にしない
7. 同一内容を2つのイベントが追加 → 一方を断定せず ambiguous・両方を refs に
8. 多重度: イベントは `X` を1回追加、hunk は `X` を2回 → full 扱いにしない
9. **一度削除され別主体が同じ行を再追加** → 確定帰属しない（内容一致の限界を示す最重要反例）
10. 符号違い: イベントは `X` を削除、hunk は `X` を追加 → 一致扱いしない
11. 巨大イベントの偶然ヒット → 弱める
12. 別ファイルの同一内容 → 候補から除外
13. イベントゼロ → 従来どおり `uncaptured`（refs 空・confidence null）
14. 同一ファイルにイベントはあるが情報量のある一致なし → `uncaptured`

### 非退行
15. スパンが健全なら内容一致に関係なく `linked`(1.0)
16. 汚染スパンが交差するなら従来どおり構造的 `broken`(0.4)
17. `candidate` は既存の強い構造的証拠を上書きしない

### 表示・集計
18. `ask` / `triage` が `candidate` を「hook捕捉外」と表示しない
19. `ingest` の集計で `candidate` を `linked` にも `uncaptured` にも数えない

## 7. 受入条件

1. 既存テストが全て通る（期待値を緩めない）
2. 上記テストが全て通る
3. `method: content-match` が永続化され、confidence だけで証拠種別を推測させない
